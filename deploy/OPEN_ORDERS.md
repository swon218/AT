# 미체결 조회·정정·취소

## 원인과 경로

기존 OrderEntryPanel의 미체결 분기는 안내 문구만 렌더링했다. 기존 신규 주문 성공/실패와 별개로 증권사 미체결을 읽는 연결 자체가 없었다.

- 브라우저: `UnfilledOrdersPanel` → `useOpenOrders` → `openOrdersApi`.
- Production: 같은 출처 `/api/order-management` → Vercel `api/order-management.js` → 기존 서버 전용 `ATLAS_API_ORIGIN`.
- Node: `GET /api/account/orders/open`, `POST /api/orders/:broker/manage`. 개발용 Vite는 같은 요청을 Node의 `/api/order-management` 별칭에 전달한다.
- 인증: 매 요청 Supabase 회원 세션 → 저장된 해당 회원·해당 증권사 개인 자격증명. 관리자/다른 회원 키 대체 없음. 전체 4개 등록 조건 없음.
- 계좌 선택은 HMAC 참조. NH 기존 요약/신규 주문도 참조를 해석하며 구형 화면의 본인 원계좌 선택 입력은 호환 처리한다. 응답에 원계좌번호는 반환하지 않는다.

## 공식 명세와 구현 범위

| 증권사 | 조회 | 정정 | 취소 | 제한 |
|---|---|---|---|---|
| 키움 | ka10075, 전체 종목·양방향·통합 거래소, 연속조회 | kt10002 | kt10003 | 확인된 현금·정규장 지정가 정정. 취소는 확인된 현금·거래소 주문. 잔여 중 명시적 양의 수량을 보내며 0=전량을 쓰지 않음 |
| 토스 | 개인 계좌의 OPEN 국내 KRW 주문 전량. 이름은 개인 `/api/v1/stocks?symbols=` 최대200종목씩, 5분 메타데이터 캐시 | `/api/v1/orders/{id}/modify` | `/api/v1/orders/{id}/cancel` | 부분체결 정정은 수량 의미 불명확하여 차단. 미체결 DAY 지정가만 정정. 취소는 잔여 전량. OPEN이 제공하지 않는 외부/시간외 주문은 임의 생성하지 않음 |
| NH | 본인 계좌 목록 → 당일 dailyOrderExecution, 미체결 필터, cts | 차단 | 차단 | 통합주문번호와 원시장주문번호의 대응이 공식 명세로 입증되지 않음. 사용자 추가 안내 없음 확인 후 조회 전용으로 제한 |
| KB | 당일 SSQM2341, 미체결 필터, nxt_key | SSAM1805 | SSAM1806 | 확인된 현금 유형만. 표준종목번호(ISIN)는 개인 SIQM4900의 실제 단축코드로 변환, 문자열 자르기로 추정하지 않음. 쓰기에는 원 표준코드 보존. 해외IP 실연결은 별도 미검증 |

키움·NH·KB는 당일 조회 범위이며 토스는 OPEN 제공 범위다. 이름/시각/체결수량 미제공은 가짜 값으로 채우지 않는다. 연속조회는 최대50페이지·18초 범위에서 확인하며 누락/반복 커서·불완전 행은 부분 조회로 표시하고 변경을 제한한다.

정정은 주문 유형·거래소·매매 방향을 유지하며 취소 후 재주문으로 대체하지 않는다. 공통 입력은 양의 정수·잔여수량·금액 범위를 검증한다. 2천원 이상 최소5원 단위를 검사하고, 토스에서 검증된 주식/ETF/ETN 유형은 해당 호가단위를 추가 검사한다. 다른 유형을 이름으로 추정하지 않으며 상세 호가단위·상하한·세션·가용 수량은 증권사 최종 검증을 따른다. 입력 가격·수량을 임의로 보정하지 않는다.

## 중복 방지·상태

`ORDER_MANAGEMENT_SUPABASE.sql`을 먼저 적용한다. 기존 broker_order_requests 테이블과 데이터를 변경하지 않는다. 새 테이블은 원계좌/키/토큰/증권사 원문을 저장하지 않는다. 브라우저 역할과 service_role의 직접 테이블 권한은 없고, 서버 전용 RPC만 service_role에 허용한다.

서버는 fresh 개인 미체결 전체 조회로 계좌·원주문·버전을 대조한 뒤 검증된 범위만 예약한다. 같은 요청 ID의 다른 입력은 거부한다. 원주문별 트랜잭션 자문 잠금 및 활성 요청 유일 인덱스가 다른 ID의 동시 전송도 막는다. 범위 잠금은 키 교체에도 유지된다. 재시작 시 미확정 요청을 다시 실행하지 않는다.

- pending: 예약 이후 결과 미저장. 잠금 유지.
- accepted: 새 접수번호 수신. 처리 완료 아님. 전체 조회에서 원주문의 실제 상태가 바뀐 경우에만 observed로 전환하여 후속 사용자 요청 허용.
- uncertain: 전송 후 시간초과/비정상 응답/결과 저장 실패. 자동 해제·재전송 없음. 증권사 앱에서 확인 필요.
- rejected: 전송 전 검증 실패 또는 명확한 업무 거절. 같은 ID는 재실행하지 않음.

accepted 주문이 목록에서 사라졌다고 체결/취소 완료로 단정하지 않는다. 불명확한 요청은 임의 SQL로 잠금을 풀지 않는다. 운영자가 증권사에서 결과를 확인한 후 별도 절차가 필요하다.

공유 읽기를 시작하기 전에 DB 시각으로 read_marker를 취득한다. accepted 잠금 해제에는 접수 기록 이후 시작된 전체 조회만 사용한다. 접수 전에 시작한 과거 조회가 늦게 도착해 잠금을 풀지 못하며, Node와 DB 사이의 시계 차이로 이를 추정하지 않는다.

회원·증권사·키 버전·계좌별 미완료 조회만 공유하며, 결과 자체를 개인 공용 캐시로 남기지 않는다. 활성 화면·visible일 때30초 갱신, 변경 요청 후 즉시/3초/8초 제한 후속 읽기를 한다. 탭 이탈·계정/계좌 전환 시 읽기와 후속 타이머를 취소한다. 이미 전송한 쓰기는 서버에서 결과 기록까지 진행하고 자동 재전송하지 않는다. 잔고는 같은 후속 갱신, 주문내역은 해당 화면 재진입 시 기존 경로로 다시 조회한다.

키움 공지68의 22개 지정 계좌TR에 보수적인 공통1.05초 읽기 간격을 적용한다. ka10075/kt10002/kt10003은 공지 대상이 아니며 읽기·쓰기 각5TPS 이하 간격을 구분한다. 같은 키의 계좌/연결검증/내역/미체결/재시도는 단일 API 프로세스의 공통 큐를 사용한다. 제한 오류는429, 읽기만 제한 재시도, 쓰기는 인증 재발급을 포함해 자동 재시도하지 않는다. 현재 단일 atlas-api 서비스 기준이며 여러 API 프로세스로 확장할 경우 유량 큐를 분산 공유해야 한다. 쓰기 중복 잠금은 DB 기반으로 이미 프로세스 간 공유된다.

## 로컬 검증과 한계

`npm run test:server`, `node --test tests/orderManagementProxy.test.js tests/recentOrders.test.js tests/assetSummary.test.js`, `npm run build`.

PGlite에서 SQL을 실제 실행해 권한·경쟁 요청·유일성·반복 적용 보존·DB 이미지 재로딩을 확인한다. 별도 PostgreSQL 서버의 다중 세션 경합 및 운영 Supabase 적용은 수행하지 않는다. Windows 파일 기반 PGlite 재개방은 WASM abort로 실패하여 공식 dumpDataDir/loadDataDir 경로로 엔진 재로딩을 검증했다.

`tests/support/openOrdersBrowser.html`은 로컬 모의 화면이다. 프로덕션 진입점에 포함되지 않으며 운영 API·DB·주문·Kakao를 호출하지 않는다. Chrome에서 모바일390x844/데스크톱, 두 테마, 긴 이름/많은 행 스크롤, 빈/오류/부분/오래된 상태, 계정 전환의 늦은 응답, 선택 계좌·최종 확인·Escape 포커스·모의 접수/결과불명을 확인한다.

실제 개인 키 미체결 대조, 실제 매수/매도/정정/취소는 전부 미실행이다. 사용자의 과거 실제 매도 경험을 이번 실검증으로 계산하지 않는다. 운영 회원 정보 변경·메시지·유료 AI 호출 없음.

## 사용자가 직접 수행할 실계좌 확인

1. 배포 SHA·SQL·Vercel/VPS 반영을 먼저 확인한다. 개인 계정으로 로그인하고 등록된 증권사 하나만 선택한다. 본인 계좌의 미체결과 MTS를 읽기 전용으로 대조한다. 다른 차트 종목으로 바꿔도 전체 주문이 유지되는지 확인한다.
2. 주문 시각·매매 방향·유형·거래소·주문/체결/잔여수량을 대조한다. 실제 매수·매도 검증을 별도로 기록한다. 없다면 테스트용 신규 주문을 자동 생성하지 않는다.
3. 본인이 변경하려는 미체결 주문이 있을 때만 정정을 열어 가격과 잔여수량을 입력하고 최종 확인 내용을 읽는다. NH와 토스 부분체결 정정은 앱에서 관리한다.
4. 본인이 명시적으로 확정한다. 새 접수번호와 원주문 관계를 확인하고 후속 미체결/잔고/거래내역을 MTS와 대조한다. 접수 문구를 완료로 간주하지 않는다.
5. 본인이 취소하려는 주문이 있을 때만 잔여 전량 취소를 확인·확정한다. 지원되는 키움/KB 부분 취소는 확인한 일부 수량으로만 한다. 이미 체결된 수량은 취소되지 않는다.
6. 결과 확인 필요가 보이면 반복 제출하지 말고 MTS에서 먼저 확인한다. 모달을 닫는 버튼은 거래 취소가 아니다. 회원·증권사·계좌 전환과 로그아웃 후 이전 목록이 사라지는지도 확인한다.
