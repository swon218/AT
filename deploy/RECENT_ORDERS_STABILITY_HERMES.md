# 헤르메스 전달문 · 최근 주문 조회 안정화

현재 운영 기준은 `5e4e9e0333834aaed86e805f92e9296e985169ac`입니다. 사용자가 전달한 **`최근 주문 조회 안정화`의 최종 전체 SHA**만 `codex/dashboard-orders-only`에서 선별 배포하세요. `main` pull/merge, 실험실 전환, DB·환경파일 변경은 하지 마세요. 이 문서는 이전 최근 주문 선택 배포 문서의 후속 지시입니다.

## 변경과 한계

- 클라이언트는 선택 변경 후 350ms가 지나면 마지막 선택만 조회합니다. 그 전에 선택·계좌·사용자·키가 바뀌면 예약 요청을 취소하고 이전 데이터는 즉시 숨깁니다.
- 서버는 매 요청 개인 세션·등록 키를 먼저 확인한 뒤, 동일 사용자·증권사·개인 키·선택 계좌·조회 날짜의 **진행 중인 조회만** 합칩니다. 목록과 상세 모두 적용하며 완료·실패한 개인 응답을 보관하는 캐시는 없습니다. 사용자·키·계좌·날짜가 다르면 공유하지 않습니다.
- 브라우저 연결 종료를 서버에 연결했습니다. 다른 요청이 같은 작업을 사용하면 유지하고, 마지막 요청이 취소되면 750ms 유예 후 중단합니다. 유예 중 새 선택 요청이 같은 작업을 필요로 하면 재사용합니다. 이미 증권사에 도달한 요청까지 회수할 수 있다는 의미는 아닙니다. 전체 제한은 기존 25초입니다.
- HTTP 429를 확인한 사용자·증권사·키에는 `Retry-After` 대기(1~300초, 없으면 30초)를 적용합니다. 계좌를 바꿔도 이 대기 중에는 재호출하지 않습니다. 자동 재시도는 없습니다. 다른 사용자의 대기 상태나 개인 결과를 공유하지 않습니다.
- 목록은 증권사별 `error: rate_limited` / `timeout` / `broker_unavailable`을 구분하고 성공 결과를 유지합니다. 상세의 429는 HTTP 429와 `Retry-After`로 반환합니다. 키움 계좌 요약 성공만으로 주문내역 성공을 판정하지 마세요.
- 선택 0~4개, 최근 5거래일의 통합 최신 5건을 오래된 순으로 표시, 최신 거래 마지막 행, ‘더보기’ 준비 중 동작은 유지합니다.
- **토스 요약·시장 조회 등 다른 경로의 호출 한도까지 이 변경이 통합 제어하는 것은 아닙니다.** 실제 한도 초과와 키움 업무 오류 해결을 보장하는 배포가 아닙니다. 기존 키움 실패 원인은 아직 미확정입니다.

## 제한적 서버 로그

일반 요청·응답 로깅의 `silent`는 유지합니다. 조회 실패 시에만 별도 루트 logger의 warn 메시지 `Recent orders broker lookup failed`를 기록합니다. 같은 진행 중 작업의 구독자마다 중복 기록하지 않으며, 단순 선택 취소나 429 대기 차단은 반복 기록하지 않습니다.

허용 필드: 증권사 ID, 사전에 정한 조회 단계(`token`, `accounts`, `kt00007`, `kt00009`, `orders_open`, `orders_closed`, `dailyOrderExecution`, `ssqm2341`, 불명 시 `lookup`), 분류, timeout 여부, HTTP 상태, 6자리 이하 숫자 형태의 업무 오류 코드. 전체 제한 시간 초과의 단계는 `lookup`일 수 있습니다. 오류 객체·메시지·스택·요청 URL/쿼리·원본 응답·사용자 ID·키·토큰·계좌번호는 기록하지 않습니다. 문자열 업무 코드 등 허용 범위 밖은 생략하며 원문을 대신 출력하지 마세요.

## 검증 및 적용

먼저 기존 서비스 경로·사용자와 운영 SHA를 확인하고 변경을 보존하세요. 기존 안전한 배포 절차의 별도 staging checkout에서 최종 SHA를 검증합니다. 셸 변수 `DEPLOY_SHA`는 사용자가 전달한 전체 SHA로 설정합니다.

```bash
git status --short
git fetch origin codex/dashboard-orders-only
git switch --detach "$DEPLOY_SHA"
git merge-base --is-ancestor 5e4e9e0333834aaed86e805f92e9296e985169ac HEAD
git log -1 --format='%H %s'
git log -1 --format='%H %s' -- deploy/RECENT_ORDERS_STABILITY_HERMES.md
git diff --name-only 5e4e9e0333834aaed86e805f92e9296e985169ac HEAD
node --test server/orderReadCoordinator.test.js server/recentOrders.test.js tests/recentOrders.test.js tests/assetSummary.test.js
npm run test:server
npm run build
```

로컬 검증: 서버 **119/119**, 프런트 유틸·보유종목 **6/6**, 빌드 성공. 집중 명령은 28개입니다. 테스트에는 실제 증권사 조회·실주문이 없고, 연결 종료 검증은 127.0.0.1의 모의 HTTP 서버만 사용합니다. 추가 의존성·환경변수·DB/Python 변경은 없습니다. 로컬 브라우저 모의에서는 240ms 동안 네 번 선택을 바꿔 목록 요청 1건·최종 두 증권사 조회 2건만 추가되는 것, 토스 429 중 키움 결과 유지, 전체 해제 안내를 확인했습니다.

1. 변경 목록이 주문 조회·오류 메타데이터·모의 테스트·이 문서 범위인지 확인하세요. `lab/`, 실험실 UI·DB·unit/timer 변경이 있으면 중단합니다.
2. 기존 방식으로 승인 SHA를 Node API에 반영하고 **`atlas-api`만** 재시작합니다. `atlas-ai`·타이머·운영 venv는 변경하지 마세요. 목록·상세 비로그인 401과 서비스 active를 확인합니다.
3. Vercel은 **동일 SHA의 선별 브랜치 Preview**를 Production으로 승격합니다. 인증이 없으면 사용자에게 Preview 배포 ID와 승격 필요 여부를 알리고 기다립니다. `main` 배포를 대신 승격하지 마세요. 새 Production 배포 ID·SHA·운영 도메인 일치를 확인해야 프런트 완료로 보고할 수 있습니다.
4. 화면 검증은 우선 `node tests/recentOrdersBrowserHarness.mjs` → `http://127.0.0.1:15176/tests/recentOrders.html` 모의 환경을 사용합니다. ‘빠른 선택 변경 검증’과 ‘요청 횟수 확인’, ‘토스 요청 한도 초과’ 시나리오가 있습니다. 검증 서버는 마친 후 종료합니다.
5. 운영 실계좌 진단은 **사용자가 별도로 요청하기 전까지 추가 호출하지 마세요.** 승인되면 기존 한도 대기 종료 후 대시보드에서 키움만 한 번 선택하고, 해당 시각의 제한적 warn 필드를 대조합니다. 버튼 연속 전환·자동 재시도·반복 새로고침·다른 카드 강제 갱신은 하지 않습니다. 로그가 없으면 원인을 추정하지 말고 실제 응답 상태와 관찰 범위를 보고하세요.
6. 토스는 계좌 요약의 확인된 429와 주문내역의 실제 오류를 분리하세요. 키움의 `stage`, `upstreamStatus`, `brokerCode`, `timeout`이 확보되면 이를 보고하고 원문·비밀정보를 출력하지 마세요. KB `unconfigured`는 별도 상태이며 호출하지 않습니다.

최종 보고에는 VPS SHA·active, Vercel Production SHA·배포 ID, 테스트 수, 모의 검증과 실계좌 검증 여부를 분리하세요. 푸시나 빌드 성공만으로 실제 4사 주문 조회 성공을 보고하지 마세요.
