# 자동매매 V1 운영 반영

이 문서는 배포 절차입니다. 실계좌 주문 검증 또는 LIVE 활성화 완료를 뜻하지 않습니다.

## 적용 범위와 기본 상태

- 기존 Supabase 관심종목·전략 V2·암호화 개인 자격증명 저장소를 재사용합니다. 신규 7개 `trading_v1_*` 테이블과 서비스 전용 RPC는 설정, 일회용 시작 확인(5분·시작 직전 재검증), 실행 스냅샷, 계좌 lease, 예약금, 주문 의도, 체결, 이벤트를 저장합니다.
- 기존 분석·알림 에이전트에 주문 도구를 추가하지 않습니다. 모델/프롬프트는 변경하지 않습니다.
- 프런트는 main의 Vercel 자동 배포, 서버는 `/opt/atlas`의 `atlas-api.service`, 신규 드라이버는 `atlas-trading-worker.service`입니다. 브라우저는 조회와 명시적 제어 요청만 수행합니다.
- 신규 worker는 **disabled/inactive**, `ATLAS_TRADING_WORKER_ENABLED=false`, `ATLAS_TRADING_LIVE_ENABLED=false`가 기본입니다. 기존 `KIWOOM_ORDERS_ENABLED` 값은 변경하지 않습니다.
- PAPER는 데이터 저장 범위와 상태가 LIVE와 분리됩니다. V1에서 가상 체결 엔진을 제공하지 않으며 PAPER 시작은 차단됩니다.

## 지원 계약

키움 개인 API만 KRX 현금 주문을 지원합니다. `kt00011`의 미수 없는 주문가능현금/100% 증거금/미수불가 한도를 보수적으로 적용합니다. `kt00018` 현재 현금 보유분, `ka10075` 미체결, `kt00007` 주문, `kt00009` 개별 체결을 대조합니다. 신용·복수 보유구분·거래정지·관리종목·불확실 수량은 차단합니다.

토스는 공식 주문 명세에서 KRX 전용 라우팅이 확인되지 않았습니다. NH는 통합주문번호와 취소용 원시장주문번호의 관계가 불명확합니다. KB는 보유분/신선한 개인 KRX 시세/정확한 체결 대사 계약이 확인되지 않았습니다. 이 세 어댑터는 이유를 표시하고 V1 실행을 차단합니다. 다른 증권사나 운영자 키로 대체하지 않습니다.

공식 자료는 `server/tradingBrokerGateway.js`의 `TRADING_BROKER_SOURCES`에 있습니다. 실제 개인 API·모의투자·실주문 검증은 별도입니다.

## 실행 정책

- 지표 신호는 기존 실험실 계산기를 확정 일봉에 적용합니다. 이전 거래일의 신호를 다음 허용 KRX 개장 후 60초 안에서만 평가합니다. 장중 늦게 시작하면 지난 개장 신호를 추격하지 않습니다. 읽기 도중 기회가 지나도 실제 POST 직전에 다시 차단합니다.
- 익절·손절 전용 전략은 사용자가 `신규 1회 진입` 또는 `기존 보유분 관리`를 선택합니다. 인수 수량/평균가를 시작 확인에 표시하며 기존 매수 시각을 만들어내지 않습니다. 1회 진입·인수 실행은 청산 후 완료합니다.
- 매수는 최신 KRX 가격을 기준으로 제한된 지정가, 청산은 KRX 현금 시장가입니다. 가격 도달과 실제 체결은 다릅니다. 시세는 15초 이내의 실제 KRX 체결시각을 요구하며 워커는 기본 10초 간격으로 계좌를 순차 처리합니다. API 호출/계좌 수에 따라 실제 관측 간격은 더 길며 순간 도달을 놓칠 수 있습니다.
- 매수 미체결 60초 경과 또는 정지/위험기준 도달 시 소유한 진입 잔량만 취소 요청하고 실제 결과를 대조합니다. 부분체결 수량은 누락하지 않습니다. 이미 확인된 보유분의 익절·손절 관리는 취소 결과와 정합성을 확인한 뒤 계속합니다.
- 계좌 lease와 원자적 예약으로 같은 현금을 두 실행이 중복 사용할 수 없습니다. 순서는 시작 당시 관심종목 순서, 시작 시각, 실행 ID입니다. 신뢰할 수 있는 예약금 반영 증거가 없는 접수 주문은 종결까지 보수적으로 예약을 유지하여 뒤 종목이 일시적으로 자금 부족 대기할 수 있습니다. 실제 현금 원장을 두 번 차감하는 것은 아닙니다.
- 영속 dispatch는 의도별 한 번만 승인합니다. 토큰·유량 대기 이후 실제 HTTP 직전에도 일회용 DB 전송 허가로 lease/정지/관심종목을 확인합니다. 전송 결과 불명은 자동 재전송하지 않습니다. 주문번호를 확인하지 못하면 신규 진입을 막고 정합성 확인 상태를 유지합니다.
- 정지는 신규 진입 중단입니다. 잔량을 확인하고 보유분 보호를 계속합니다. 별도 관리 중단을 확인한 경우에만 자동 보호를 중단하며 강제 청산하지 않습니다.
- API 삭제·재등록은 설정 epoch를 바꾸어 이전 실행의 자격증명을 무효화합니다. V1은 안전을 위해 다른 증권사 키 설정 변경도 기존 실행의 재확인을 요구할 수 있습니다. 설정/전략 수정이 기존 실행 스냅샷을 바꾸지 않습니다.
- 비용 미확정 손익은 순손익으로 표시하지 않습니다. 진입/청산 기록은 실제 체결만 사용합니다. 매입가 선과 완료 거래 마커는 OHLC 데이터에 삽입하지 않습니다.

## 배포 순서

1. TARGET의 조상/서버 변경 범위/clean 상태를 확인하고 OLD SHA와 Vercel 직전 정상 배포를 기록합니다. 운영 중인 자동매매가 이미 있다면 아래 별도 절차를 먼저 따릅니다.
2. DB 담당자가 복구 가능한 백업을 확보한 뒤 **TARGET의 `deploy/TRADING_AGENT_V1_SUPABASE.sql` 전체**를 인증용 Supabase SQL Editor에 적용합니다. 기존 SQL은 재실행하지 않습니다. 권한 `false,false,true`, 7개 테이블 RLS와 직접 접근 차단, 무결성 `0,0`을 확인합니다. 기존 회원 데이터는 삭제하지 않습니다.
3. 격리 worktree에서 `npm ci`, `node --test server/trading*.test.js tests/tradingDb.test.js tests/tradingPresentation.test.js`, `npm run build`를 실행합니다. 운영 의존성/lockfile을 임의 업그레이드하지 않습니다.
4. `/etc/atlas/atlas.env`를 root:root 0600의 별도 안전 백업 후, 두 활성화 플래그를 명시적으로 false로 설정합니다. 새 `ATLAS_TRADING_INTERNAL_SECRET`은 승인된 비밀 관리 경로로 생성·입력하고 출력하지 않습니다. 기존 암호화·개인키·AI·알림 설정은 변경하지 않습니다.
5. 전용 로그인 불가 계정 `atlas-trading`을 마련합니다. `/opt/atlas` 코드/의존성 읽기와 loopback API 접근만 허용합니다. 개인 키 저장소/서비스 DB키/일봉 DB 쓰기 권한을 주지 않습니다. `/etc/atlas/trading.env`는 root:atlas-trading 0640으로 `ATLAS_TRADING_API_ORIGIN=http://127.0.0.1:3000`과 같은 내부 비밀만 저장합니다. API/DB/broker 비밀 전체 환경파일을 복사하지 않습니다.
6. API를 정상 중지하고 atlas 사용자로 TARGET까지 `git merge --ff-only`합니다. 새 unit을 `/etc/systemd/system/atlas-trading-worker.service`에 설치하고 `systemd-analyze verify` 후 daemon-reload합니다. 신규 unit은 disable 상태를 유지하고 API만 기동합니다. AI·평가·알림·DART·일봉 수집·WAL guard는 재시작하지 않습니다.
7. API health 200, 비인증 `/api/agent/trading` 및 config/preview/start/stop/chart 401, 외부/Origin 있는 internal tick 401, Vercel의 internal 경로 비노출을 확인합니다. 승인된 내부 secret의 loopback tick은 `disabled`, 주문 POST 0이어야 합니다. 환경/로그/응답 원문을 출력하지 않습니다.
8. Vercel Production SHA가 TARGET인지 확인합니다. 회원 UI에서는 설정/실행/진행상황, 연결 확인, 저장과 시작 분리, LIVE 비활성 표시와 시작 버튼 비활성을 확인합니다. 운영 키 저장/삭제·실행 시작·매수·매도·정정·취소를 검증 목적으로 실행하지 않습니다.

## 향후 운영 활성화

배포와 분리된 운영자 승인 후, 본인 계좌 읽기 전용 실조회·공식 제한과 일봉 품질·거래일 달력·키움 주문 활성화 상태·복구 담당 체계를 확인합니다. 실주문/모의투자 검증은 사용자 별도 허가와 계획 없이 수행하지 않습니다. 활성화를 요청받으면 API의 두 플래그를 true로 바꿔 API만 재시작하고 신규 전용 worker를 enable/start합니다. **이 단계로 기존 설정이 자동 시작되지는 않습니다.** 사용자가 화면의 시작 확인에서 개별 저장 설정을 명시적으로 시작해야 세션이 생성됩니다.

## 장애와 롤백

최초 배포에서 세션/주문이 없다면 신규 worker를 stop/disable하고 두 플래그 false를 유지한 채 API만 중지, OLD의 clean detached checkout으로 전환 후 API를 기동합니다. Vercel도 OLD의 정상 Production을 재승격합니다. 신규 테이블·기록을 DROP/DELETE하지 않습니다.

실제 포지션·미체결·전송불명이 생긴 뒤에는 worker 중지/구버전 복귀가 보호 관리를 끊을 수 있습니다. 먼저 신규 진입을 금지하는 사용자 정지 요청을 처리하고 소유 미체결/체결/보유분과 각 세션을 읽기 전용 대조합니다. 소유 잔량 취소가 필요한 경우 기존 안전한 정지 흐름으로 처리하고, 사용자의 명시적 관리 중단 전까지 보호를 조용히 해제하지 않습니다. 불명확 주문을 재전송하거나 다른 서비스로 인수하지 않습니다. 포지션이 남은 상태의 장애 복구는 담당자가 증권사 화면으로 안전 조치를 확인한 후 진행하며, 자동 시장가 청산은 실행하지 않습니다. DB의 intent/fill/position/event/lease/reservation 기록과 환경 백업을 보존합니다.
